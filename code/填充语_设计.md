# 填充语：松手先说一句，再等答案（2026-10-27）

> 需求原话：「在回复之前，我希望板子可以自己说一些话，比如"我知道了""让我想一下""正在查阅"」
> 状态：**服务端全部完成并测过；固件写完、编译通过，但发声那一步（`fillerPlay()`）留着没填 —— 等板子**。
> 体积：写这份时整包是 2,267,315 / 72%；2026-10-27 接上语音唤醒后整包变成 **3,126,315 / 99%**，只剩 19,413 字节。

## 一、它要解决的问题

一次交互的空窗有多长（实测）：

| 阶段 | 耗时 |
|---|---|
| 录音（说到静音 1.2 秒自动停） | 本地，无空窗 |
| 上传 | 0.3 秒（局域网） |
| 百度识别 | 0.8~1.2 秒 |
| 大脑：本地话术 / 平台 | **1.5 秒** / **6~13 秒** |
| 回来下载音频 | 0.1~0.3 秒 |

所以**从闭嘴到它开口，静音 1.5~14 秒**。填充语要填的就是这一段。

## 二、为什么最后是"受理 + 轮询"而不是"流式"

最初选流式（一次连接、先发一行状态、答案好了再发第二段），两个实验都做了：

- **实验一**：服务端立刻吐一行 → 响应头 0.03 秒到 ✓（`Transfer-Encoding: chunked`）
- **实验二**：服务端先算 6 秒再吐 → 响应头 **6.02 秒**才到 ✗

结论：**头不会自己提前到，必须靠"立刻吐一行"来催**。这一行让流式成立，但也意味着
**板子必须自己解析 chunked 分帧** —— 而板子那层恰恰是当时唯一没法验的部分。

所以改成"受理 + 轮询"：板子侧不需要任何新机制（就是 `http.GET()` + `getString()`，
和提醒轮询同一套，那套已经在板子上跑通过）。体验一样，风险落在能测的服务端。

## 三、协议

```
POST /v1/voice?async=1
     ← 立刻：{"ok":true,"state":"accepted","id":"…","poll":"/v1/voice/result?id=…"}

GET  /v1/voice/result?id=…
     ← 算着：{"ok":true,"state":"working","elapsed":1.2}
     ← 好了：{"ok":true,"state":"done","elapsed":7.4, voice_text/asr_text/audio_url/…}
     ← 过期：{"ok":false,"state":"gone"}
```

- **不带 `async` 参数时，行为与 2026-10-27 之前完全一样** ✓（零点回归风险）
- 结果留 3 分钟、最多同时存 12 个；超时或野号回 `gone`，板子据此说"再说一次"
- ASR 失败仍走"识别失败了，你再说一遍好吗"（不是 error 状态）；只有大脑那一步抛出去才是 error

## 四、投放策略（模拟器跑出来的，不是拍脑袋）

`tools\填充语时序.py` 把这套门控在电脑上跑一遍，输出时间线。三种策略对比（**最长静音 / 答案被拖后**）：

| 场景 | burst（接得紧） | spread（摊开 2.5 秒） | final（第三句压到 6 秒） |
|---|---|---|---|
| 1.5 秒（本地话术） | 0.00 / 0.20 | 0.00 / 0.20 | 0.00 / 0.20 |
| 4 秒 | 0.18 / 0.39 | 2.30 / 0.00 | **0.79 / 0.00** |
| 7 秒 | **2.61** / 0.00 | 2.58 / 0.00 | 2.87 / 0.19 |
| 13 秒（长尾） | 8.61 / 0.00 | **3.61** / 0.00 | 5.81 / 0.00 |

**选 `final`**：它是唯一在常见场景不吃亏、又把长尾从 8.6 秒救到 5.8 秒的。
改策略只动一个常数（`FILLER_GATE_MS`，6 秒）。

⚠️ **模拟器还揪出一条规则**（第一版漏了）：**填充语一旦开始播就必须播完** ✗ ——
1.5 秒就出答案的路径里，硬切填充语，用户听到的是"好的，嗯我查一…"，
像卡带。所以答案要等当前这句播完（最多多等 1.3 秒），这比切断好得多。

## 五、音频从哪来（`code/server/filler.py`）

- edge-tts 原生 24kHz 单声道 PCM_16（板上实测能播 ✓），语速 +8%（短句说慢了显拖沓）
- **生成后必须裁头尾静音** ✗ —— edge 塞的空白很长：「好的」原长 1.10 秒，裁完 0.48 秒；
  三句填充语平均省 33%，语气词省 55%
- 裁音用 `array('h')` 自己算 RMS：**Python 3.13 删了 `audioop`**（PEP 594），实测 import 就炸
- 清单在 `语音\filler_manifest.json`；改了文案会自动重生成并清掉孤儿文件
- 接口 `GET /v1/fillers` 返回 `{hi:[…], fill:[…], max_fill:3}`，板子上电缓存

现在这套（5 条语气词 + 3 条填充语）：

| id | 类型 | 时长 | 文案 |
|---|---|---|---|
| hi01 | 语气词 | 0.48s | 好的 |
| hi02 | 语气词 | 0.47s | 嗯嗯 |
| hi03 | 语气词 | 0.43s | 行 |
| hi04 | 语气词 | 0.49s | 好嘞 |
| hi05 | 语气词 | 0.63s | 哦好的 |
| fill01 | 填充语 | 1.22s | 嗯，我查一下 |
| fill02 | 填充语 | 1.33s | 稍等，我看看 |
| fill03 | 填充语 | 1.11s | 这个我得查查 |

**2026-10-27 试听确认**：这 8 条全部可用（负责人听完 `语音\试听_语气词.wav`、`语音\试听_填充语.wav` 后的结论），不用再挑。

合计 6.2 秒音频、约 300 KB（24k 单声道）—— 缓存到 PSRAM 或那 9 MB FAT 分区都行，
**flash 一 KB 都不用动**（当时整包 72%；接唤醒后 99%，但填充语音频仍然放在文件系统里，不占 app 分区）。

为什么不要单独一个「嗯」：「嗯」0.34 秒，实测听着太短像卡了一下；「嗯嗯」（0.47 秒）顶上。
为什么不要「我知道了」：松手时用户刚说完，这句听起来像「别说了」。
